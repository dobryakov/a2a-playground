# Протокол A2A-over-git

**Координация агентов проектной команды через общий git-репозиторий**

- Статус: рабочий черновик (v0.4)
- Место в репозитории: `.agents/PROTOCOL.md`
- Область: несколько людей в одной команде (напр. аналитик, программист, менеджер), агенты которых совместно ведут произвольные текстовые артефакты в git (WBS, спека, документ, код — что угодно).

Этот документ — источник истины протокола. Он нейтрален к модели, инструменту и предметной области: ему одинаково следуют человек, Claude-агент и любой другой агент. Протокол определяет только **конверт** — как сообщения передаются, адресуются и связываются в треды, и какого ответа требует каждый тип. *Что* делать с сообщением по существу — решают ролевые промпты и скиллы участника (раздел 14), а не этот протокол. Принуждение к конверту даёт MCP-сервер (раздел 13); привязку к репозиторию — тонкий `AGENTS.md` (раздел 14).

---

## 1. Назначение

Дать команде простую механику, при которой агенты разных участников координируются, оставляя структурированные сообщения прямо в репозитории. Один участник делает изменение — его агент оставляет сообщение; другой делает `git pull` — его агент видит сообщение и реагирует так, как велит его роль.

Ключевая ставка: **git уже стоит в каждой команде**. Он даёт неизменяемую историю, авторство, метки времени и готовый аудит-трейл без единого нового сервера. «Занести в новую команду» = склонировать репозиторий; протокол приезжает вместе с ним.

---

## 2. Принципы и инварианты

Всё остальное — следствия этих правил. Их нарушение ломает систему.

1. **Транспорт — файлы репозитория, а не метаданные коммита.** Канал — файлы в `.agents/msgs/`, а не текст git-коммита. Так сообщения переживают `rebase`, не требуют пустых коммитов и машинно разбираются.
2. **Одно сообщение = один файл с уникальным именем.** Два агента, пишущие одновременно, никогда не конфликтуют при слиянии — они пишут в разные файлы. Каталог сам по себе является инбоксом.
3. **Ничему из формы истории и часов не доверяем как источнику истины.** `rebase` переставляет коммиты, часы участников расходятся. Причинность и треды держатся на ребре `in_reply_to` (стабильные `id`), а не на порядке коммитов или wall-clock `ts`.
4. **Состояние выводится, а не хранится.** Тред и статус любого обязательства вычисляются свёрткой неизменяемого лога сообщений на чтение — нет общего мутируемого объекта состояния (он был бы записью-в-конфликт).
5. **Общая рабочая ветка.** Все пишут в одну ветку, `pull`/`push` часто. Никакого merge-протокола между ветками.
6. **Курсор агента — локальный, множество message-id.** «Что уже обработано» хранится вне репозитория (в `.git/`), у каждого агента своё, как множество `id` — не хешей и не отметок времени.
7. **Идентичность агента — локальная, из конфига сервера.** `agent-id` не хранится в версионируемых файлах. Поле `from` проставляет MCP-сервер, а не модель из запроса — это же защищает от подмены отправителя.
8. **Запрещён force-push, а не rebase.** Опасна перезапись *опубликованной* истории; локальный `rebase` своих неопубликованных коммитов безопасен.
9. **Агент не импровизирует на конфликтах и решениях.** Merge-конфликт данных (в т.ч. при `rebase` во время пуша) или выход за рамки → агент не «чинит» наугад, а эскалирует конкретному человеку.
10. **Агент не реагирует на собственные сообщения** и соблюдает лимит глубины цепочки ответов (защита от зацикливания).

## 3. Идентичность и адресация

Единица участия — **участник**: человек + его агент, с общим стабильным `participant-id` (`analyst`, `dev`, `manager`). У участника две конечные точки:

- `<id>-agent` — агент участника (напр. `manager-agent`);
- `<id>-human` — человек-владелец (напр. `manager-human`).

Правила:

- **`from` всегда проставляет MCP-сервер** из локального конфига — модель его не передаёт. Сервер владеет идентичностью *своего участника* и вправе подписаться как свой `-agent` или свой `-human`, но **не как чужой участник**. Это закрывает подмену.
- **`to` — список конкретных конечных точек.** Никакого абстрактного `"human"`: эскалация идёт конкретному человеку, напр. `to: ["manager-human"]`.
- Идентичность живёт в **конфиге/окружении запуска MCP-сервера** (не в репозитории). Резервный вариант — нетслеживаемый `.git/agents/whoami`.

```

    ├── msgs/                     # инбокс: одно сообщение = один файл
    │   ├── 2026-07-28T14-30-00Z__analyst-agent__a1b2c3d4.json
    │   ├── 2026-07-28T14-52-10Z__manager-agent__e5f6a7b8.json
    │   └── ...
    └── archive/                  # свёрнутые старые сообщения (раздел 10)
```

Локальное (не версионируемое) состояние живёт в `.git/`, вне отслеживания:

```
repo/.git/agents/
    ├── whoami                    # опц.: идентичность участника, если не в конфиге сервера
    ├── analyst-agent.cursor
    └── manager-agent.cursor
```

## 5. Формат сообщения

Сообщение — небольшой JSON-файл. Словарь заимствован у A2A (Message/role) и ACP/FIPA-ACL (перформативы), чтобы позже можно было съехать на «настоящий» A2A-транспорт.

**Имя файла:** `<ts>__<from>__<id>.json` (двоеточия в `ts` заменены на дефисы). Сортируемо по времени, уникально по `id`.

**Пример — уведомление аналитика менеджеру:**

```json
{
  "id": "a1b2c3d4",
  "ts": "2026-07-28T14:30:00Z",
  "from": "analyst-agent",
  "to": ["manager-agent"],
  "type": "inform",
  "in_reply_to": null,
  "root": "a1b2c3d4",
  "refs": {
    "files": ["wbs.csv"],
    "locator": "row 4.2"
  },
  "body": "Добавил работу 4.2 «Интеграция API» — новый скоуп по запросу клиента."
}
```

**Поля:**

| Поле | Обяз. | Смысл |
|---|---|---|
| `id` | да | Уникальный идентификатор сообщения. Стабилен при любых перестановках коммитов. |
| `ts` | да | Момент создания, UTC ISO-8601. Только для отображения/сортировки, не для корректности (инвариант 3). |
| `from` | да | Конечная точка отправителя. **Проставляет сервер**, не модель (раздел 3). |
| `to` | да | Список конечных точек-адресатов (`*-agent` / `*-human`). |
| `type` | да | Речевой акт (раздел 6). |
| `in_reply_to` | нет | `id` сообщения-родителя. `null` — начало треда. |
| `root` | да | `id` корневого сообщения треда. **Производное, всегда есть:** `= in_reply_to == null ? id : parent.root`. Проставляет сервер; даёт группировку без обхода графа. Никогда не минтуется вручную. |
| `refs` | нет | На что ссылается сообщение: `files` + свободный `locator` (форма зависит от формата артефакта, раздел 9). |
| `body` | да | Человекочитаемое тело. |

Обрати внимание: **`context_id` нет.** Тред — это граф ответов, а не именованная группа (раздел 7).

**Связь с коммитом — односторонняя, через трейлер.** Сообщение не хранит хеш своего коммита (коммит не может содержать собственный хеш). Направление — «коммит → сообщение» через трейлер `Msg-Id` (раздел 8).

## 6. Речевые акты и контракт ответа

Тип сообщения задаёт, какого ответа он *ожидает* и кто вправе его дать. Это описывается обобщённо и content-agnostic — здесь и живёт ответ на «что делает агент-получатель на структурном уровне». *Содержание* ответа — уже дело роли участника (раздел 14).

| `type` | Смысл | Открывает обязательство? | Закрывается |
|---|---|---|---|
| `inform` | Сообщение факта («добавил работу», «выполнено»). | нет | — |
| `question` | Запрос информации. | да | `answer` |
| `request` | Запрос действия. | да | `accept` / `reject`, затем `inform` о выполнении |
| `propose` | Предложение решения (перенести, сократить, выйти за рамки). | да — **адресат человек-владелец** | `accept` / `reject` |
| `answer` | Ответ на `question`. | закрывает | — |
| `accept` | Согласие на `request` / `propose`. | закрывает | — |
| `reject` | Отказ на `request` / `propose` с обоснованием. | закрывает | — |

Правила конверта (их проверяет сервер, раздел 13):

- Закрывающий тип должен соответствовать родителю: `answer` отвечает только на `question`; `accept`/`reject` — только на `request`/`propose`.
- `propose` и любое решение о выходе за согласованные рамки адресуется человеку-владельцу (`*-human`), не агенту. Агенты не утверждают такое автономно.

## 7. Треды и состояние обязательств

Никакого отдельного идентификатора темы. **Тред — это транзитивное замыкание `in_reply_to`**, а идентичность треда — `id` его корневого сообщения (поле `root` даёт его за O(1), но при желании выводится обходом родителей вверх). Предмет обсуждения может быть каким угодно — тред не привязан к типу артефакта.

**Состояние выводится свёрткой, не хранится (инвариант 4).** Обязательство открывается сообщением `question`/`request`/`propose` и закрывается ответом соответствующего типа среди его потомков. Статус треда — это фолд над его неизменяемыми сообщениями:

- *открытые обязательства* = открывающие сообщения без закрывающего ответа в потомках;
- *на ком висит* = адресаты (`to`) открытого обязательства.

Сервер по запросу отвечает «что открыто на мне» — это и есть A2A-подобное «input-required / resolved», но без мутируемого Task-объекта.

**Лимит зацикливания — глубина цепочки ответов** (`depth = 1 + depth(parent)`), а не счётчик по группе. При превышении агент не продолжает, а ставит `question`/`request` человеку. Порог — параметр `MAX_DEPTH`, по умолчанию `10` (заведомо больше любой нормальной переписки; срабатывание означает, что агенты зациклились).

**Напоминание о незакрытом обязательстве** — параметр `OBLIGATION_TIMEOUT`. По умолчанию **выключен** (без авто-напоминаний): команда включает его, когда поймёт свой темп общения, и тогда пингуется тот, кто должен ответ. До этого открытые обязательства просто видны в `pending()` — их можно смотреть вручную.

## 8. Формат коммита

Изменение артефакта и сопровождающее сообщение попадают в **один коммит**, в который кладётся git-trailer (встроенный механизм, как `Signed-off-by`) — мостик для людей и tooling.

```
feat(wbs): работа 4.2 «Интеграция API»

Agent: analyst-agent
Msg-Id: a1b2c3d4
For: manager-agent
```

Заголовок — в стиле Conventional Commits. Трейлеры `Agent` / `Msg-Id` / `For` позволяют по `git log` найти сообщение по коммиту, не открывая `.agents/msgs/` — та самая односторонняя связь из раздела 5.

## 9. Работа с произвольным артефактом

Слой сообщений **не знает и не должен знать, что редактируется.** Это может быть таблица, документ, спека, код. Отсюда два следствия.

**Ссылки универсальны.** `refs = { files, locator? }`, где `locator` — свободная строка, осмысленная для формата: `"row 4.2"` для таблицы, `"## Риски"` для markdown, `"func parse_wbs"` или `"L120-L138"` для кода, либо ничего — файл целиком.

**Конфликт-терпимость — свойство формата, а не протокола.** Протокол требует лишь одного: на *реальный* merge-конфликт агент не импровизирует, а эскалирует (инвариант 9). Политика по умолчанию — **всегда эскалировать**; давать агенту сводить конфликт самому стоит только по мере накопления доверия и только там, где цена ошибки мала (мелкая правка формулировки — можно; бюджет, чужая правка — всегда человек). Как снизить частоту конфликтов — уже рецепт под формат:

- **Строчно-ориентированные данные (CSV, JSONL):** одна запись = одна строка, стабильная сортировка по ключу — правки в разные строки мёржатся чисто.
- **Ещё надёжнее:** одна запись = один файл, а сводный вид собирается на лету — конкурентные добавления не конфликтуют вовсе.
- **Проза / код / markdown:** конфликты — обычное дело git; тут нет «структурного» лекарства, работает общее правило: сомнительный конфликт → эскалация человеку.

Пример строчно-ориентированного артефакта (WBS):

```csv
id,parent,name,owner,estimate_days,status
4.1,4,Проектирование API,analyst,3,planned
4.2,4,Интеграция API,dev,5,planned
4.3,4,Тесты интеграции,qa,2,planned
```

## 10. Состояние агента: курсор

Курсор отвечает на «какие сообщения я уже обработал».

- Хранится **локально**, в `.git/agents/<agent-id>.cursor` — не в репозитории. Это состояние на запись только у владельца; в общей истории оно давало бы конфликты и шум. `.git/` структурно не отслеживается — его не закоммитить случайно (в отличие от `.gitignore`, который можно сломать широким `git add`).
- Курсор — **множество обработанных message-id**, и только. Не хеши (перезаписываются `rebase`) и не время (часы расходятся, инвариант 3).

```json
{ "processed_ids": ["a1b2c3d4", "c9d0e1f2", "f0a1b2c3"] }
```

**Компакция — через архивацию, не по времени.** Старые сообщения периодически переносятся из `.agents/msgs/` в `.agents/archive/`; раз заархивированное сообщение не попадает в скан инбокса, его `id` можно убрать из курсора. Это единственный безопасный способ сжатия — он опирается на факт «файла нет в инбоксе», а не на предположение о монотонности времени.

## 11. Работа с общей веткой

### 11.1. Гонка пуша

Общая ветка вводит не merge-конфликт, а гонку пуша: два агента почти одновременно `pull → commit → push`, второй push отлетает с `non-fast-forward`. Обработка в цикле: `push` отклонён → `git pull --rebase` (переиграть свои неопубликованные коммиты) → повторить `push`, несколько ретраев. `rebase` своих неопубликованных коммитов безопасен, файлы-сообщения переживают его целиком.

**`rebase` во время пуша может упереться в конфликт артефакта.** Если чужой коммит правил тот же участок, `git pull --rebase` встанет. Это уже не гонка пуша, а инвариант 9: `git rebase --abort` и эскалация человеку. Сообщения при этом не теряются (отдельные файлы, не конфликтуют).

### 11.2. Запрет force-push

Опасна перезапись *опубликованной* истории (force-push / non-fast-forward). Разрешаем безопасный случай, запрещаем опасный:

- **Хостинг:** protected branch с запретом force-push на рабочую ветку.
- **Свой bare-репозиторий:** `receive.denyNonFastForwards = true` — git отклоняет любой не-fast-forward push на уровне протокола.

## 12. Защита от зацикливания

1. Агент **не реагирует на собственные сообщения** (`msg.from == me` → пропуск).
2. **Лимит глубины цепочки ответов** `MAX_DEPTH` (по умолчанию `10`, раздел 7). При превышении — не продолжать, а поставить `question`/`request` человеку.
3. **Человеческий чекпойнт** на `propose` и решениях о выходе за рамки.

## 13. MCP-сервер координации

**Транспорт — Python stdio.** Агент участника (Claude Code, Codex, что угодно) поднимает сервер как локальный дочерний процесс по stdio: ни портов, ни веб-сервера, ни OAuth — прямо работает на «легко занести в команду». Сервер работает с локальным клоном; синхронизация между участниками по-прежнему через git pull/push, а не через сервер. Контракт инструментов от транспорта не зависит — при желании потом сменить на хостируемый вариант, не трогая инструменты.

Идентичность (`me`) сервер берёт из своего окружения/конфига — она **не** приходит от модели, поэтому у публичных инструментов нет параметров `from`/`agent_id`. Сервер обеспечивает **конверт**: проставляет отправителя, валидирует схему, адресатов и соответствие ответа родителю, выводит статус обязательств, двигает курсор, делает push-с-ретраем. **Что делать с сообщением по существу — сервер не решает; это ролевые промпты и скиллы участника** (раздел 14).

Ниже **псевдокод** контракта. Реализация: пакет `mcp_a2a/` в корне репозитория (Python stdio).

```text
me = server.config.identity        # напр. "manager-agent"; НЕ приходит от модели

# --- Публичные инструменты MCP ---

tool post_message(to[], type, body, in_reply_to?, refs?):
    validate_recipients(to)
    if in_reply_to:
        parent = read_msg(in_reply_to)
        validate_response_type(parent.type, type)   # answer→question, accept/reject→request|propose
        root = parent.root
    else:
        root = null                                  # проставим id после генерации
    msg = {
      id: random_id(), ts: now_utc_iso(), from: me,  # from проставляет сервер (раздел 3)
      to, type, body,
      in_reply_to: in_reply_to ?? null,
      root: root ?? "<self-id>",
      refs: refs ?? {}
    }
    validate_schema(msg)
    path = ".agents/msgs/{fs_safe(msg.ts)}__{me}__{msg.id}.json"
    write_file(path, json(msg))
    git_add(path); git_add(refs.files or [])         # сообщение + правка артефакта = один коммит
    git_commit(message = summary(msg),
               trailers = { "Agent": me, "Msg-Id": msg.id, "For": join(to) })
    push_with_retry()
    return msg.id


tool read_inbox():
    git_pull(rebase = true)
    cursor = load_cursor(me)
    inbox = []
    for path in sort_by_ts(list(".agents/msgs/*.json")):   # ts — лишь для показа
        msg = read_json(path)
        if me in msg.to and msg.from != me and msg.id not in cursor.processed_ids:
            inbox.append(msg)
    return inbox


tool get_thread(root_id):
    msgs = [m for m in all_msgs() if m.root == root_id]     # O(1)-группировка по root
    return { messages: sort_by_causality(msgs),
             state: fold_obligations(msgs) }                # открытые/закрытые (раздел 7)


tool pending():                                            # что открыто и висит на мне
    return [ob for ob in fold_obligations(all_msgs())
            if ob.open and me in ob.to]


# --- Внутренние помощники ---

internal push_with_retry(max_tries = 5):
    for i in 1..max_tries:
        if git_push() == OK: return
        result = git_pull(rebase = true)
        if result.has_conflict:                            # конфликт артефакта при rebase — инвариант 9
            git_rebase_abort(); escalate_to_human("Конфликт при rebase — нужен человек"); return
    escalate_to_human("push не прошёл после ретраев")


internal mark_processed(msg):
    cursor = load_cursor(me); cursor.processed_ids.add(msg.id); save_cursor(me, cursor)

internal surface_to_human(msg):
    notify_owner(msg)                                      # человек не крутит цикл сам
```

**Цикл агента** — конверт обеспечивает сервер/цикл, а решение по существу делегируется роли:

```text
on each session:
    for msg in read_inbox():
        if msg.to contains human_owner(me):
            surface_to_human(msg); mark_processed(msg); continue     # адресовано человеку
        if reply_depth(msg) > MAX_DEPTH:
            post_message(to=[human_owner(me)], type="question",
                         in_reply_to=msg.id, body="Лимит глубины — нужен человек")
            mark_processed(msg); continue

        act = role_decide(msg)          # <-- ЭТО ролевой промпт/скилл участника, не протокол

        if act.changes_artifact and merge_conflict(act):             # инвариант 9
            post_message(to=[human_owner(me)], type="question",
                         in_reply_to=msg.id, body="Конфликт, свести не смог: " + act.detail)
        else if act.needs_human:                                     # propose/решение — человеку
            post_message(to=[human_owner(me)], type="propose",
                         in_reply_to=msg.id, body=act.text, refs=act.refs)
        else:
            apply(act)                                                # правка артефакта, если есть
            post_message(to=act.to, type=act.reply_type,             # answer/accept/reject/inform
                         in_reply_to=msg.id, body=act.text, refs=act.refs)

        mark_processed(msg)
```

`role_decide` — единственное место доменной логики, и оно **вне протокола**: у каждого участника своё, в его AGENTS.md / системном промпте / скиллах.

## 14. Размещение правил

| Слой | Что это | Где живёт |
|---|---|---|
| Истина / «почему» | Этот протокол (конверт) | `.agents/PROTOCOL.md` в репозитории |
| Принуждение / «как» | MCP-сервер | локальный stdio-процесс у каждого; знает `me` |
| Привязка / «делай здесь» | Тонкий инструкционный файл | `AGENTS.md` в корне |
| **Реакция по существу** | **Доменная логика роли** | **ролевые промпты и скиллы участника — вне этого протокола** |

Нижняя строка — принципиальная: протокол задаёт только контракт конверта (какой ответ требует тип, кто вправе его дать), а *что именно* решить по содержанию — целиком на стороне каждого участника. Поэтому механику можно внедрить, не описывая предметную область.

Привязку кладём в **AGENTS.md**, а не `CLAUDE.md`: AGENTS.md — кросс-инструментальный стандарт (Linux Foundation / AAIF), который читают десятки агентов; CLAUDE.md специфичен для Claude Code. Если Claude-специфика нужна — CLAUDE.md импортирует AGENTS.md через `@AGENTS.md`. `AGENTS.md` общий и версионируемый, поэтому идентичности конкретного агента в нём быть не может — она приехала бы одинаковой ко всем (раздел 3).

**Пример `AGENTS.md` (держать тонким):**

```markdown
# AGENTS.md

Репозиторий использует протокол координации A2A-over-git.
Полная спецификация: `.agents/PROTOCOL.md` — прочитай перед работой.

## Обязательное поведение (конверт)
- В начале сессии вызывай `read_inbox`; смотри `pending` — что висит на тебе.
- Любое изменение общих файлов сопровождай `post_message`.
- Не редактируй `.agents/msgs/` вручную — только через инструменты MCP-сервера.
- Отвечай типом, закрывающим обязательство: `answer` на `question`, `accept`/`reject` на `request`/`propose`.
- На конфликт или выход за рамки не импровизируй — ставь вопрос/предложение человеку-владельцу.
- Не делай force-push в рабочую ветку.
- Свой `agent-id` не читай из репозитория и не указывай — его проставляет сервер.

## Как реагировать по существу
См. ролевой промпт/скиллы этого участника — они определяют доменные решения.
```

## 15. Как поднять систему с нуля

1. Общий git-репозиторий и одна рабочая ветка (`main` или `agents`).
2. Защита ветки от force-push: protected branch или `receive.denyNonFastForwards = true`.
3. Добавить в репозиторий `.agents/msgs/`, `.agents/archive/` и этот файл как `.agents/PROTOCOL.md`.
4. Положить в корень `AGENTS.md`; при необходимости `CLAUDE.md` с `@AGENTS.md`.
5. Выбрать формат артефактов и стратегию конфликт-терпимости под него (раздел 9).
6. У каждого участника поднять MCP-сервер (Python stdio) с уникальной идентичностью (`<id>-agent`/`<id>-human`) в конфиге/окружении запуска — только там, не в репозитории.
7. Дать каждому агенту ролевой промпт/скиллы с доменной логикой (`role_decide`).
8. Убедиться, что курсоры и (опц.) `whoami` лежат локально в `.git/agents/` и не отслеживаются.

## 16. Как этим пользоваться: сквозной пример

Аналитик добавляет работу в WBS, агент менеджера сверяет её с бюджетом.

**Шаг 1.** Агент аналитика дописывает строку `4.2` и вызывает `post_message(to=["manager-agent"], type="inform", …)`. Сервер проставляет `from: "analyst-agent"` и `root` (= собственный `id`, т.к. это начало треда):

```json
{
  "id": "a1b2c3d4", "ts": "2026-07-28T14:30:00Z",
  "from": "analyst-agent", "to": ["manager-agent"],
  "type": "inform", "in_reply_to": null, "root": "a1b2c3d4",
  "refs": { "files": ["wbs.csv"], "locator": "row 4.2" },
  "body": "Добавил работу 4.2 «Интеграция API» — новый скоуп по запросу клиента."
}
```

Один коммит (данные + сообщение) с трейлером `Msg-Id: a1b2c3d4`, затем `push_with_retry`.

**Шаг 2.** Агент менеджера вызывает `read_inbox()`, получает `inform`. Его **ролевой скилл** сверяет 5 дней с остатком бюджета и видит перебор. По контракту конверта решение о выходе за рамки — человеку, поэтому агент ставит `propose` на `manager-human` (тот же `root`, ответ на исходное):

```json
{
  "id": "e5f6a7b8", "ts": "2026-07-28T14:52:10Z",
  "from": "manager-agent", "to": ["manager-human"],
  "type": "propose", "in_reply_to": "a1b2c3d4", "root": "a1b2c3d4",
  "refs": { "files": ["wbs.csv"], "locator": "row 4.2" },
  "body": "4.2 (+5 дней) выводит квартал за бюджет на ~2 дня. Перенести на Q4 или сократить до 3 дней?"
}
```

Агент показывает это человеку (`surface_to_human`). В этот момент `pending()` у `manager-human` содержит открытый `propose`.

**Шаг 3.** Человек выбирает вариант; его агент оформляет решение как `accept`/`reject` (`in_reply_to: e5f6a7b8`, тот же `root`) и при необходимости правит `wbs.csv`. Это закрывает обязательство — `get_thread("a1b2c3d4").state` теперь показывает тред разрешённым. Любой участник восстановит всю цепочку через `get_thread("a1b2c3d4")` по причинности, независимо от того, как перетасовались коммиты при пушах.

Итог: изменение, обоснование, проверка бюджета и решение человека — одна прослеживаемая цепочка в обычном git, без внешней инфраструктуры и без привязки к формату артефакта.

## 17. Опора на стандарты

- **git trailers** — встроенные структурированные метки коммита (`git interpret-trailers`).
- **Conventional Commits** — человекочитаемый префикс заголовка.
- **A2A (Agent2Agent, Linux Foundation)** — модель Message/роли; поля выровнены под неё для forward-совместимости.
- **ACP / FIPA-ACL** — перформативы и пары «акт → ответ» как основа раздела 6.
- **AGENTS.md** — кросс-инструментальный стандарт файла-привязки.
- **In-Reply-To / References (email)** — образец тредирования по ответам без отдельного id темы (наш `in_reply_to` + производный `root`).

## 18. Открытые вопросы для команды

- Автослияние тривиальных конфликтов: по умолчанию — всегда эскалация (раздел 9); границу «что агент вправе сводить сам» команда сдвигает по мере доверия.
- Криптоподпись коммитов, если авторства через конфиг сервера недостаточно.
- Политика/периодичность архивации `.agents/msgs/ → .agents/archive/` (от неё зависит компакция курсора).
- Тайм-аут «висящих» обязательств (`OBLIGATION_TIMEOUT`): по умолчанию выключен; включить и подобрать значение, когда прояснится темп общения команды (раздел 7).
